## 本讲要解决的问题

代码写得再好，如果：
- **README 乱糟糟**，别人不知道怎么用
- **issue 描述一句话**，维护者没法帮你
- **PR 没 tests、没描述**，没人敢 merge
- **邮件语气强硬**，对方直接黑名单

就会变成"技术能力很强，但没人愿意和你合作"。本讲讲代码之外的"软技能"——**写得清楚、说得得体**，这是工程师长期价值的倍增器。

## 1. 好 README 的结构

README 是项目的门面。**用户点进来的前 30 秒决定了他会不会继续用**。

**推荐结构**（从上到下）：

```markdown
# 项目名

一句话描述（最多 15 字）

[![CI](badge)](link)  [![PyPI](badge)](link)

## ✨ 特性

- 关键卖点 1
- 关键卖点 2
- 关键卖点 3

## 🚀 快速开始

```bash
# 一条命令装上
pip install xxx

# 一条命令跑起来
xxx --help
```

## 📘 示例

最小可运行例子（5-10 行）展示核心功能

## 📖 文档

- [完整文档](docs/)
- [API 参考](docs/api.md)
- [FAQ](docs/faq.md)

## 🛠 开发

```bash
git clone ...
make install-dev
make test
```

## 🤝 贡献

见 CONTRIBUTING.md

## 📄 许可证

MIT
```

**反面典型**：
- ❌ 开头先讲哲学、动机、作者背景（用户只想看"怎么用"）
- ❌ 长篇大论的背景介绍放在"快速开始"之前
- ❌ 只有代码没有输出示例

## 2. 写一个清晰的 Issue

提 issue 前先自问：**对方能不能靠这份 issue 在 5 分钟内复现问题？**

### 2.1 模板

```markdown
## 问题描述
一句话说清发生了什么。

## 如何复现
最小代码/命令：
```bash
git clone ...
cd ...
python3 main.py --foo bar
```

## 期望行为
我以为会打印 "hello"。

## 实际行为
报错（贴完整 traceback）：
```
Traceback (most recent call last):
  ...
```

## 环境
- OS: macOS 15.3 (arm64)
- Python: 3.11.7
- 版本: xxx 0.2.1
- 相关依赖版本（如有）

## 我已尝试
- 看过 README，没找到相关说明
- 试过 xxx，同样失败
```

### 2.2 黑暗三连
绝对不要这样提 issue：
```
标题：不能用
正文：跑不起来，怎么办？
```

维护者看见这种 issue 会直接关掉。

## 3. 写一个能被 merge 的 Pull Request

### 3.1 PR 描述模板

```markdown
## 背景
（这次改动的来由，比如 fix #123 / 实现 xxx 需求）

## 改动内容
- 新增 `layers/linear_attn.py` 中的 kv_update 实现
- 修复 `mfu/mfu.py` 的 fp8 分支数据表索引错误

## 设计思路
（为什么这样改，考虑过哪些替代方案）

## 验证
- [x] 跑通 `example/qwen3-8B/sim.sh`
- [x] 新增 `tests/test_linear_attn.py`，全部通过
- [x] 对比修正前后 TTFT 数值差异 < 1%

## 向后兼容
无破坏，CLI 参数完全兼容。

## 遗留问题 / 后续计划
（如果有）
```

### 3.2 PR 规范

- **小**：一个 PR 只做一件事。200 行以内的 PR 通过率远高于 2000 行的
- **独立**：不要夹带无关重构（另开 PR）
- **有测试**：bug fix 必须有回归测试
- **能通过 CI**：推上来一定得通过 CI，不要让维护者帮你修格式
- **响应 review**：review 意见及时回复，即使不接受也要说明理由

## 4. 技术写作：文档的三种类型

**没有一种"万能文档"**。不同读者、不同场景需要不同形态。

| 类型 | 目的 | 读者状态 |
|------|------|---------|
| **Tutorial（教程）** | 带我动手做一次 | 初学者，需要成就感 |
| **How-to Guide（操作指南）** | 解决一个具体任务 | 有经验，遇到特定场景 |
| **Reference（参考）** | 查一个 API 的准确定义 | 随时查，不想读文章 |
| **Explanation（原理）** | 理解为什么这么设计 | 想深入，有时间 |

**反面典型**：很多项目把这四种混在一起写，谁看都累。

**推荐做法**：目录结构直接对应：
```
docs/
├── tutorial/
├── how-to/
├── reference/
└── explanation/
```

## 5. 邮件与消息沟通

### 5.1 结构化

```
主题：具体、可搜索（不是"求助"、"请教")

正文：
  [背景]一句话
  [问题]一句话
  [我尝试过]要点
  [期望]你能帮我做什么

签名：名字、联系方式
```

### 5.2 中英文共通原则

- **主语明确**：别说"然后出错了"，说"运行 xxx 命令后出现 yyy 错误"
- **语气温和**：避免"为什么这么差"、"这明显是 bug"这类判断式用语
- **尊重时间**：不要一上来铺垫 5 段，先说要什么
- **结论先行**：第一句话就说清你的诉求

### 5.3 常见反面

```
❌ "在吗？"       → 直接提问
❌ "有空吗？"      → 直接说事
❌ 凌晨 3 点连续 10 条消息  → 整理成一封邮件
❌ 私信社区维护者讨论公共问题  → 发到公开 issue/论坛，让更多人受益
```

## 6. 开源社区协作

### 6.1 提贡献前的功课

- [ ] 读 `CONTRIBUTING.md`
- [ ] 读 `CODE_OF_CONDUCT.md`
- [ ] 看最近 10 个已合并 PR 的风格
- [ ] 搜 issue/PR 区，确认想法没人提过
- [ ] 小改动：直接 PR；大改动：先开 issue 讨论

### 6.2 被 reject 怎么办

维护者不接受你的 PR 是常态。常见原因：
- 项目方向不匹配
- 代码风格/架构不合
- 引入额外依赖
- 测试不充分

**应对**：
1. 礼貌询问具体原因
2. 尝试改进
3. 如果根本方向不合，**fork 出去自己维护**也是光荣的

### 6.3 成为 contributor 的路径

1. 从**文档**开始（typo、翻译、补例子）——最容易被 merge
2. **小 bug fix**——门槛低，有回归测试
3. **补测试**——维护者最喜欢
4. **实现小 feature**——先开 issue 讨论
5. 长期活跃 → 可能被邀请成为 maintainer

## 7. 自我推广（但不 cringe）

### 7.1 简历上的技术项目描述

不要写：
> "参与了 XXX 系统的开发"

要写：
> "从 0 设计并实现 XXX 模拟器的核心计算层，将 Qwen3-8B 的 TTFT 预测误差从 15% 降至 3%，代码贡献 5000+ 行，已被团队用于 8 个生产项目的容量规划"

公式：**你做了什么 + 带来了什么数字级的结果 + 有多少人/项目在用**。

### 7.2 技术博客

- 每解决一个有深度的 bug，写一篇文章
- 每读完一篇有价值的论文，写一份带自己理解的笔记
- 每用熟一个工具，写一份 cheatsheet

好处：
- **强迫自己真正理解**（讲得出来才是懂）
- **建立个人品牌**
- **面试时别人能搜到你**

### 7.3 社交网络

- **GitHub**：绿格子 ≠ 有用，但长期坚持会积累真实项目
- **X / 知乎**：分享自己的学习、项目进展
- **LinkedIn**：完善履历，和同行建立联系
- **微信/Slack 社群**：混到核心社区，学习氛围 + 机会

## 8. 职业发展视角

- 代码能力是**入场券**，**沟通和写作能力是天花板**
- 技术工程师 →  技术负责人的分水岭不是代码写得多好，而是：
  - 能不能写清楚需求文档
  - 能不能主持一次会议得出决策
  - 能不能说服团队采纳你的方案
  - 能不能用 2 分钟讲清楚一个系统
- **公开可见的作品**（GitHub 项目、博客、演讲）> 简历上的一行字
